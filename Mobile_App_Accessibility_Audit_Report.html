Form field causes unexpected change

A change of context occurs without warning when the user changes the setting of a user interface control. CURRENT BEHAVIOR: 1. With VoiceOver on, swipe to Show Password button. 2. Success Criteria
3.2.2
Screenshot
Recommended Fix
RULE: Changing an element's value MUST NOT automatically trigger a change of context, unless the user is adequately advised ahead of time. HOW TO FIX Swift/SwiftUI: Fix this issue by using ONE of the following techniques: 1. Ensure that entering text into a TextField or TextView, toggling a switch or selecting an item from a PickerView does not result in a substantial change in context including: 1) submitting a form automatically 2) Navigate to the next screen 3) additional keyboard focus changes 4) any other change that could confuse or disorient the user. 2. Inform users ahead of time of such behavior by methods such as the text label for the UI control or some advisory text placed before the control that cautions the user of this behavior. BACKGROUND: People expect that selecting a link or a button may cause a change of context - such as a opening a new screen or modal, moving focus to another control, a submitting a form. Whenever the mere act of entering text into an edit box, checking a checkbox or radio button, or navigating to an option in a select control causes an unexpected change in context, some users - especially people with vision or cognitive disabilities - may become quite disoriented or confused. Changes in context should only occur when selecting a link or button - not when changing the setting of a switch button, checkbox or radio button - unless the user is informed ahead of time. This will ensure that users can interact with a screen in a predictable manner.

Serious Issue 1
Page/Component Name
WelcomeBack Screen
Summary
Font size does not respond to Accessibility Settings
Description
Font size does not respond to resizing from Accessibility Settings. CURRENT BEHAVIOR: 1. In Accessibility settings, increase the font size to maximum (slide to rightmost). 2. All the screen content does not resize to 200% of baseline. EXPECTED BEHAVIOR: 2. Text that is smaller than 200% of the app's baseline text size resizes to 200% of baseline. NOTE: The application of WCAG Success Criteria 1.4.4 Resize Text to native mobile applications is nuanced. Allowing EVERY bit of text in a view to scale to 200 percent bigger than its original size often creates more problems for users than it solves. Furthermore, text resizing and reflow come into conflict a lot! Some controls lose meaning when they are on multiple lines and ""portrait mode"" being the default makes turning single lines of text into multiple lines of text when scaled up really easy. RECOMMENDED APPROACH Don't scale ALL text to 200% of its original size. Treat the default size of your body text as a baseline and ensure everything can get to 200% of that size. For example, if heading or navbar titles are already 200% of the default body text, no further scaling is required. When text is resized to 200% of baseline, the end result is no overlapping or truncating of non-scrollable elements.

HOW TO FIX: Swift: Fix this issue by ensuing: 1. not to use fixed size fonts e.g. .systemFont(ofSize: 20, weight: .regular). These will not resize based on the user's accessibility settings. 2. Use UIFontMetrics to set the fonts and always enable adjustsFontForContentSizeCategory property to update font size as per settings.   visibleLabelObject.adjustsFontForContentSizeCategory = true HOW TO FIX: SwiftUI: Fix this issue by not to use fixed size fonts e.g. .font(.system(size: 20)). These will not resize based on the user's accessibility settings. REFERENCE: Apple: https://developer.apple.com/documentation/uikit/uicontentsizecategoryadjusting/1771731-adjustsfontforcontentsizecategor BACKGROUND: People who have low vision may not be able to read text at its default size. Content must be flexible enough to be scaled to 200% by the screen without having text cut off or functionality lost.

Summary
Does not rotate to new orientation
Description
When the device is rotated, the content does not adjust to the new display orientation. CURRENT BEHAVIOR: 1. Enable the rotate screen mode in the device settings. 2. Open the app with the device in portrait orientation and rotate to the landscape mode. 3. The app remains on portrait view and does not change to landscape view. EXPECTED BEHAVIOR: 3. The orientation of the content is not locked to either landscape or portrait mode unless a specific orientation is essential for the functionality. NOTE: The W3C working group that maintains the WCAG guidelines has debated the question about whether or not Success Criterion 1.3.4 Orientation applies to native mobile applications and has not come to a conclusion. They have deferred an opinion to the WCAG2ICT Task Force. Therefore, we raise this issue to allow you to weigh the risk of not allowing for orientation changes or planning for it now if / when a determination is made that it is applicable. Deque’s strong recommendation is that Success Criterion 1.3.4 Orientation be taken into account on both phone and tablet devices – most certainly on tablets.
Success Criteria
1.3.4
Screenshot
Recommended Fix
RULE: The orientation of the user interface and content MUST not be locked to either landscape or portrait unless a specific orientation is essential for the functionality of the app. HOW TO FIX: Swift/SwiftUI: Fix this issue by ensuring that the application does not restrict the screen to a particular display orientation. This can be accomplished by ensuring that Deployment Info options such as Portrait, Landscape Left and Landscape Right are enabled under the Xcode Target > General tab. BACKGROUND: When a mobile application is locked to a default screen orientation, people who have a preferred device orientation (e.g. portrait or landscape) - such as people with a motor disability who have a tablet mounted to their wheelchair - may not have the ability to change the orientation of their device. Mobile applications must allow users to view and operate content in either portrait or landscape orientation and allow users to adjust their display orientation as needed while interacting with the content without losing access to information or functionality. This allows users with disabilities to use the screen orientation that meets their specific needs.
